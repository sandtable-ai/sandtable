Writing a domain by hand is the main cost of adopting sandtable. `sandtable init` drafts one from what a customer hands over during discovery, then leaves a person to review it. Every inferred item stays visible as a `TODO` or `review: pending` until someone accepts it.

| Input | Drafts | Model |
|---|---|---|
| `--openapi` | world tables, seed rows from examples, tools | none: deterministic |
| `--sop` | invariants, each quoting its source sentence | Claude |
| `--transcripts` | personas, tasks and fictional seed rows | Claude |

<Warning>
The SOP and transcript steps call Claude. They have been verified in live runs on the bundled freight sources ([results](/results)), but a model can still misread a rule or a call. Treat every drafted item as a proposal until a person accepts it.
</Warning>

## The whole flow

<Steps>
  <Step title="Draft from the API">
    ```bash
    npx sandtable-ai init --openapi path/to/openapi.yaml -o sandtable
    npx sandtable-ai validate sandtable
    ```
    Writes `sandtable/sandtable.yaml`, a placeholder `policy.md` and an empty `tasks.yaml`. It refuses to overwrite existing files unless you pass `--force`. It reads OpenAPI 3.x, in YAML or JSON. It writes nothing for a Swagger 2.0 spec (convert it to OpenAPI 3 first) or for a spec it can't draft a single tool from.
  </Step>
  <Step title="Add invariants from the SOP">
    ```bash
    npx sandtable-ai init --sop policy.md -o sandtable
    ```
    Appends invariants to the existing domain and replaces the placeholder `policy.md` with the SOP.
  </Step>
  <Step title="Add tasks from transcripts">
    ```bash
    npx sandtable-ai init --transcripts calls/ -o sandtable
    ```
    Appends personas, tasks and any fictional seed rows the tasks need.
  </Step>
  <Step title="Review, lint, then run">
    ```bash
    npx sandtable-ai review sandtable              # what still needs a human decision
    npx sandtable-ai lint sandtable                # ready, solvable, non-vacuous, graded (no model calls)
    npx sandtable-ai run sandtable --agent noop --user scripted   # the floor, before any real agent
    ```
  </Step>
</Steps>

You can also pass all three inputs at once: `npx sandtable-ai init --openapi api.yaml --sop policy.md --transcripts calls/ -o sandtable`. The steps run in the order above.

## From an OpenAPI spec (deterministic)

No model is involved: the same spec always produces the same draft.

| OpenAPI | Draft |
|---|---|
| `/loads/{load_id}` | table `loads` with key `load_id` |
| a collection without an item path | key from the schema (`<singular>_id`, then `id`), else `<singular>_id` |
| `GET /loads/{load_id}` | tool with `get: loads, key: $load_id` |
| `GET /loads?origin=&status=` | tool with `list: loads, where: {...}`; free-text strings match with `$contains`, enums and numbers with equality |
| query param `default` | param `default`, applied when the agent omits it |
| `limit`, `offset`, `page`, `cursor`, … | ignored (pagination) |
| `POST /bookings` | tool with `create: bookings, values: {body fields}` |
| `PUT/PATCH /orders/{id}` | tool with `update: orders, key: $id, set: {body fields}` |
| `/customers/{customer_id}/orders` | parent params become filters and create values |
| `POST /orders/{id}/cancel` (no GET) | action: a `get` on the parent plus a review note to model the effect |
| a body param named like another table's key | existence `check` on that table |
| a body field that is an object, or an array of scalars or objects (`items: [{ sku, qty }]`) | a nested param with its `properties` or `items`, `$ref`s resolved, up to 3 levels deep; the op writes the whole value (`items: $items`) |
| a schema composed with `allOf` | its members' properties and required lists merged, in bodies, responses and params |
| a field or param named `@type` or `pickup-window` | param `at_type` or `pickup_window`, since `$` references only name letters, digits and `_`; the op still writes `"@type": $at_type` |
| a `{param}` in the path that the spec doesn't declare | a required string param |
| `example` on a response schema or its media type, and each `value` in the media type's `examples` (an `externalValue` is not fetched) | seed rows; an array is several rows. When several examples share a key, the one with the most fields is kept, with a warning |

It cannot infer some things, so they become `# TODO(review):` comments next to the tool:

- **409/422/400/403 responses**: encode the condition as a `check` with a `where`.
- **Side effects in the description** ("the load becomes booked"): add the `update` op on the other table.
- **Action endpoints**: replace the placeholder `get` with the ops that model the action.
- **Body fields it can't map**: a schema with several types, an array without `items`, or objects nested more than 3 levels deep. Add the param by hand if the agent needs it. A `oneOf` or `anyOf` field without a `type` is drafted as a string param, as before.

It also leaves out several things and lists them as warnings:

- header and cookie params
- object and array path or query params, which would be filters on a table, and body fields it can't map (also a review note)
- `DELETE` operations
- webhooks, which the API sends to the client rather than serves: OpenAPI 3.1 `webhooks`, operations' `callbacks`, and the paths where a client receives events or subscribes to them. A path counts as one only when it has a listener's shape:
  - every operation on it is tagged "notification listener" or "events subscription", and it takes only `POST` or `DELETE`, or its `POST` takes a callback URL (a string `callback` field)
  - it is `/listener/<event>`, with `<event>` a name ending in `Event`, and it takes only `POST`
  - it is `/hub` or `/hub/{id}`, and `POST /hub` takes a callback URL

  A resource such as `/hubs`, `/listener/restart` or `/events/{id}/subscriptions` is still drafted.

Tables with no examples get a `TODO: add seed rows` comment that lists the fields seen in the spec.

## From an SOP (Claude, grounded)

```bash
npx sandtable-ai init --openapi api.yaml --sop policy.md -o sandtable   # draft, then add invariants
npx sandtable-ai init --sop policy.md -o sandtable                       # add invariants to an existing domain
```

Claude reads the SOP alongside the domain's tools, params, tables and known fields, and proposes invariants in the six existing [kinds](/reference/spec#invariants), using structured outputs. Nothing it proposes is trusted as-is:

- Every invariant must **quote** the SOP. A quote that does not appear verbatim gets a warning.
- Proposals that reference an unknown tool, param, table or field, or that are incomplete, are **dropped**, and the reason is printed.
- Survivors are appended to the domain (existing comments are kept) with `review: pending` and `source: { file, quote }`.
- Conditions can compare with one value (`$ne`, `$gt`, ...), a list (`$in`, `$nin`) or presence (`$exists`). So "a call like this must include Y" drafts as a `never` whose `when` describes the call and sets `$exists: false` on Y, the argument the agent would leave out:

  ```yaml
  - id: check-refund-needs-address
    never: { tool: create_refund, when: { method: { $in: [ check, gift_card ] }, mailing_address: { $exists: false } } }
  ```
- Every rule the SOP states ends up as an invariant, a **soft rule** comment, or both. Claude first lists the SOP's rules, then maps each one. A rule that no invariant checks, or checks only in part, is written as a comment after the invariants, with its quote and why it isn't checked:

  ```yaml
    # Soft rule, not checked: A patient may cancel without a fee up to 24 hours before the visit, or later with a doctor's note.
    #   "Cancellations are free until 24 hours before the appointment, or later with a doctor's note."
    #   why: needs today's date; depends on a fact no record holds; needs an either/or condition: no record says whether there is a note
  ```

  The reason names what is missing: `needs today's date` (see [#38](https://github.com/sandtable-ai/sandtable/issues/38)), `depends on a fact no record holds`, `needs either of several tools first` (a `before` takes one first tool), `needs an either/or condition`, `needs a computed value`, or `about what the agent says` (wording, questions, read-backs, for the planned LLM-judged checks, [#16](https://github.com/sandtable-ai/sandtable/issues/16)). Read these first: they are the rules you check by hand, or rewrite your domain to make checkable, such as adding a `has_doctors_note` field.
- A rule whose drafted invariant was dropped is listed too, with the reason it was dropped. A rule Claude listed but mapped to neither is listed as `not classified by the draft`, with a warning.
- Soft rule comments are notes. They are not `soft: true` [soft invariants](/reference/spec#soft-invariants), which tool calls do check.

The SOP also becomes `policy.md` when the domain still has the placeholder. Pass `--model` to choose the drafting model (default `claude-opus-5-5`).

`--sop` makes one Claude call, and `--transcripts` one per transcript file. To see what a draft will spend before it spends anything, add `--dry-run`: it prints a plan line (calls, model, provider and a cost bound at list prices) and stops, without credentials. A real run prints the same line before its first call. After each step, `init` prints what the calls used and an estimated cost at list prices, as `run` does:

```text
  estimated cost $0.19
    model eu.anthropic.claude-sonnet-5-5: 1 calls, 9.8k in, 14.6k out, 0 cache read, 0 cache write
```

On Bedrock, a geo inference profile such as `eu.` is priced at 1.1× the global price. A model without a known price shows `n/a`.

## From call or chat transcripts (Claude, grounded)

```bash
npx sandtable-ai init --transcripts calls/ -o sandtable          # a directory of .txt/.md files, or one file
npx sandtable-ai init --openapi api.yaml --sop policy.md --transcripts calls/ -o sandtable   # all three steps
```

Each transcript becomes one task:

- a hidden-goal instruction for a simulated caller who behaves like the real one
- a scripted version of the caller's turns, so the task also runs offline
- tags, and a new or reused persona
- the end state the world must reach **if the agent follows the policy**. When the human rep broke the policy, the expectation follows the policy, not the rep.
- the `reference` calls a correct agent makes, in order with their arguments, so `lint` can prove the task solvable. They list only calls that succeed: a refusal may have lookups only

Guardrails:

- **PII is scrubbed locally before anything is sent**: emails, phone numbers and card-like numbers. Short identifiers such as order or MC numbers are kept. The model is told to replace names and companies with fictional ones.
- When the world lacks rows for the scenario, the draft adds **fictional seed rows**. A row whose key collides with an existing one drops the task.
- **A task keeps its transcript's facts.** An existing row is reused only when every fact the transcript states about it matches, so a caller who shares a name with an earlier one, but has another membership level or order, gets a row of their own. When a draft still reuses a row that contradicts its transcript, `init` keeps the task, prints a warning naming the row and each field that differs, and writes the same as a `# TODO(review):` comment above the task: give the task its own row with new IDs, or correct the task.
- Tasks that would grade nothing (no state and no `called` expectations), or that fail validation, are dropped with the reason.
- **Allowed values are shown and kept.** The model sees each param's allowed values, so a reference uses `by_mail`, not the transcript's "By Mail". When a drafted value still differs from one allowed value only in case, spaces or dashes, `init` uses that value and prints a warning such as `reference[3] update_order_return method "By Mail" → by_mail`. A value that matches none, or several, is left as drafted for the lint below to report.
- **Each drafted task is linted** as `sandtable lint` would, replaying its `reference`. A task that fails, such as a reference that doesn't reach the expected state, is kept for review: `init` prints a warning and writes a `# TODO(review): lint: ...` comment above the task. A failing reference usually points at a wrong expectation or a missing seed row.
- Survivors are `review: pending`, with the transcript and a verbatim excerpt as `source`.

<Tip>
Local scrubbing catches patterns, not every identifying detail. Read transcripts before sending them anywhere, and keep the drafted domain's seed rows fictional.
</Tip>

## Reviewing a draft

Drafted invariants and tasks carry `review: pending` and a `source` (the file and the quote they came from). Tools with review notes are marked the same way.

```bash
npx sandtable-ai review sandtable              # list what is pending, with sources
npx sandtable-ai validate sandtable --strict   # fails while anything is pending (use in CI)
```

While items are pending, runs still work, but their reports are marked **provisional**. Run `npx sandtable-ai lint` too: it catches drafted tasks that are vacuous, unreachable or unsolvable before anyone spends money running them. To accept an item, change `review: pending` to `review: accepted` or delete the line. [Review workflow](/concepts/review-workflow) covers what to check.

## What a real draft looks like

In a live run on the bundled freight sources (an OpenAPI spec, an SOP and two transcripts, in October 2026, before the example's SOP grew), `init` drafted 4 tables and 5 tools with two review notes, 9 invariants that each quote their sentence, and 2 tasks with personas and fictional seed rows. `lint` then flagged both drafted tasks as not ready, because a side effect the OpenAPI step had marked for review was not modelled yet. Details are on the [results](/results) page.
