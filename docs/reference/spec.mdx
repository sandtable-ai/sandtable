A domain lives in a directory with a `sandtable.yaml`. Any top-level value that is a relative path to a `.md`, `.yaml` or `.yml` file is inlined, so you can keep `policy: ./policy.md` and `tasks: ./tasks.yaml` in separate files. A path to a missing file is a validation error, so a misspelled path can't become the policy text.

Run `sandtable validate <dir>` after every edit. It checks the schema and every cross-reference (tables, tools, params, personas).

```yaml sandtable.yaml
name: string                # required
description: string         # who the agent works for; shown to both agent and simulated user
policy: string | ./file.md  # required: the SOP the agent must follow (the reference agent's system prompt)
max_turns: 20               # user turns per trial before it is cut off
world: { tables: ... }      # required
tools: [...]                # required, at least one
invariants: [...]
personas: [...]
tasks: [...] | ./tasks.yaml
```

<Note>
The schema is strict: an unknown key anywhere is a validation error, not a silent no-op. A typo such as `invariant:` instead of `invariants:` fails `sandtable validate`.
</Note>

## Templates

Inside tool `ops`, `checks`, invariant `where` clauses and task assertions:

- `"$arg"` is replaced by the tool call's argument value, keeping its type.
- `"${arg}"` interpolates inside a longer string: `"Load ${load_id} is not available"`.
- A condition whose argument was not passed (an optional param) is dropped, so it filters nothing.

## Where clauses

`where`, `fields` and `when` are maps of field to condition. A plain value means equality. An object of operators means all of them must hold:

| Operator | Meaning |
|---|---|
| `$eq`, `$ne` | equal / not equal |
| `$in`, `$nin` | in / not in a list |
| `$gt`, `$gte`, `$lt`, `$lte` | numeric comparison (strings compare lexically, so ISO dates work) |
| `$exists` | `true`: the field is set and not null; `false`: it is missing or null |
| `$contains` | case-insensitive substring |

## world

```yaml
world:
  tables:
    loads:
      key: load_id            # primary key field
      rows:                   # seed data; each trial starts from a fresh copy
        - { load_id: L-1001, origin: "Dallas, TX", status: available, max_rate: 2350 }
    bookings:
      key: booking_id         # created rows without a key get "<table>-<n>"
```

Every seed row needs its key field, and keys must be unique within a table.

## tools

A tool is what the agent sees (name, description, JSON-schema params) plus what it does to the world.

```yaml
- name: book_load                       # ^[a-zA-Z0-9_-]{1,64}$
  description: What it does, written for a model.
  params:
    load_id: { type: string }           # string | number | integer | boolean
    rate: { type: number, description: "All-in USD" }
    note: { type: string, required: false }
    equipment: { type: string, required: false, enum: [dry_van, reefer] }
    status: { type: string, required: false, default: available }   # used when the agent omits it
  checks:                               # preconditions the real API enforces; failing one = tool error, no writes
                                        # (skipped when the key comes from an optional arg that was not passed)
    - { table: loads, key: $load_id, where: { status: available }, error: "Load ${load_id} is not available" }
  ops:                                  # run in order, atomically (all or nothing)
    - create: bookings
      values: { load_id: $load_id, rate: $rate }
    - update: loads
      key: $load_id
      set: { status: booked }
  returns: 0                            # which op's result the agent gets back (default 0)
```

| Op | Effect | Returns |
|---|---|---|
| `get: <table>, key` | read one row; error if missing | the row |
| `list: <table>, where?, limit?` | filter rows | array of rows |
| `create: <table>, values` | insert a row | the new row |
| `update: <table>, key, set` | merge fields into a row; error if missing | the updated row |
| `respond: <value>` | no state change | the value (templated) |

Arguments are validated before anything runs. Unknown argument names, missing required ones and wrong types come back to the agent as tool errors. Representations are coerced leniently: `"2,100"` becomes `2100` for a number param, and `100101` becomes `"100101"` for a string param.

There is no `delete` op, and params are scalars only (no arrays or nested objects yet; see [#26](https://github.com/sandtable-ai/sandtable/issues/26)).

## invariants

Checked before every tool call, against the world as it is at that moment. A violation fails the trial even if the call itself then errors: attempting the forbidden action is the bug. [Invariants vs expectations](/concepts/invariants) explains when to use which.

```yaml
# `then` only after a successful `first` with the same values for `same`
- id: verify-before-book
  description: ...
  before: { first: verify_carrier, then: book_load, same: [mc_number] }

# the record keyed by an argument must exist and match `where`
- id: eligible-carrier
  description: ...
  require: { tool: book_load, table: carriers, key_arg: mc_number, where: { insurance_status: valid } }

# numeric bound on an argument: a constant or another record's field
- id: rate-ceiling
  description: ...
  limit: { tool: book_load, arg: rate, lte: { table: loads, key_arg: load_id, field: max_rate } }

# soft: checked the same way, reported as a rate, never fails a trial
- id: counter-at-ceiling
  description: ...
  soft: true
  limit: { tool: log_offer, arg: counter_offer, lt: { table: loads, key_arg: load_id, field: max_rate } }

# two referenced records must agree on a field
- id: equipment-match
  description: ...
  match:
    tool: book_load
    left: { table: carriers, key_arg: mc_number, field: equipment }
    right: { table: loads, key_arg: load_id, field: equipment }

# never call a tool (optionally: never with matching args)
- id: no-refunds-over-500
  description: ...
  never: { tool: issue_refund, when: { amount: { $gt: 500 } } }

# never say a protected value in any agent message
- id: never-disclose-ceiling
  description: ...
  never_disclose: { table: loads, field: max_rate, unless: { tool: book_load, arg: rate } }
```

| Kind | Checked | Fails when |
|---|---|---|
| `before` | on every call to `then` | no earlier successful `first` call with equal values for every arg in `same` |
| `require` | on every call to `tool` | the row keyed by `key_arg` is missing or does not match `where` |
| `limit` | on every call to `tool` | `arg` is above `lte`, below `gte`, at or above `lt`, or at or below `gt` (each a number, or a field of the row keyed by `key_arg`) |
| `match` | on every call to `tool` | `left` and `right` fields differ (skipped if either value is missing) |
| `never` | on every call to `tool` | always, or when the arguments match `when` |
| `never_disclose` | on every agent message, after the conversation | any value of `table.field` appears in what the agent said |

`never_disclose` recognizes the usual spellings of a number (`2350`, `2,350`, `$2,350.00`) without matching identifiers, longer numbers or units (`L-2350`, `12350`, `2350km`). The Unicode hyphens U+2010 and U+2011 read as `-`, so `L‑2350` is an identifier and `555‑0148` matches the value `555-0148`. An en or em dash after a number still ends it (`$2,350—final`). String values shorter than three characters are ignored, and booleans can't be protected. `validate` rejects a `never_disclose` whose field holds booleans, or only strings shorter than three characters, in the seed rows, because it could never fire. `unless` allows a value the agent successfully passed to that tool argument, such as the rate it actually booked. Give a list to allow several, for example the booked and the submitted rate: `unless: [{ tool: book_load, arg: rate }, { tool: submit_offer, arg: rate }]`.

### Soft invariants

Any invariant can be marked `soft: true`. It is checked exactly like a hard one, but breaking it never fails a trial and never changes pass^k. Instead, runs report how often it was broken:

- per trial, under `soft` in `results.json`: each soft invariant that applied, whether it was broken, and the call or message that broke it;
- per run, as a rate: the trials in which it was broken, out of the trials in which it applied. A rule applies in a trial when its tool was called, or for `never_disclose`, when the agent said anything.

The terminal summary, the HTML report and the leaderboard show the rate, for example `counter-at-ceiling 37.5% (3 of 8 trials that called log_offer)`. Use a soft invariant for behaviour the policy allows but the customer wants measured. The freight example's `counter-at-ceiling` measures how often counter-offers reach the price ceiling, which the policy permits. Anything the policy forbids stays hard. A soft violation in a `reference` replay doesn't make `sandtable lint` call a task unsolvable.

The `Soft rule` comments that `init --sop` writes are different: they note rules that tool calls can't show, such as wording or tone, for the planned LLM-judged checks ([#16](https://github.com/sandtable-ai/sandtable/issues/16)).

Every invariant also accepts `review` and `source` (see [Review workflow](/concepts/review-workflow)).

## personas and tasks

```yaml
personas:
  - id: haggler
    description: A seasoned owner-operator who always pushes on rate.

tasks:
  - id: walk-away-above-ceiling
    description: Shown in reports.
    persona: haggler
    tags: [negotiation, refusal]
    max_turns: 12                      # overrides the domain default
    user:
      instructions: |                  # hidden goal + private facts; the agent never sees this
        You need at least $1,600 and will not go lower...
      opening: "MC 100101, calling about L-1002."   # optional fixed first line
      script: [ ... ]                  # optional fixed turns for --user scripted
    reference:                         # optional: what a correct agent would do; `sandtable lint` replays it
      - { tool: verify_carrier, args: { mc_number: "100101" } }
    expect:
      state:
        - { table: bookings, count: 0 }                                # exactly N rows (with optional where)
        - { table: bookings, where: { load_id: L-1004 } }              # at least one matching row
        - { table: loads, key: L-1002, fields: { status: available } } # this row matches
        - { table: loads, key: L-9999, count: 0 }                      # this row does not exist
      called: [verify_carrier]          # each must have succeeded at least once
      not_called: [transfer_to_human]   # never attempted
      reply_includes: ["confirmation"]  # some agent message contains it (case-insensitive, U+2010/U+2011 read as -); use sparingly
```

The simulated user ends the conversation by emitting `###STOP###` when its goal is met, impossible, or it has been handed off. If that final message also has content ("Fine, book it. Bye."), the agent gets one last turn to act on it. Trials that hit `max_turns` are still graded on the end state.

The scripted user (`--user scripted`) replays `user.script` line by line, then stops. A task without `script` falls back to `opening` alone; a task with neither cannot run with the scripted user.

Tasks also accept `review` and `source`, like invariants.
